# v1.3.x — Live-ops cadence

**Window**: 2027-09-01 → ongoing
**Status**: Planned
**Owner**: Pablo (solo dev) + opcional comunidad
**Prev**: v1.2 shipped + unlock criteria PASS
**Next**: v2.0 vision (cuando DAU justifique)

Tras los 4 pilares completos, v1.3 NO es una versión monolítica — es un
modelo de cadencia continua. Releases mensuales con scope acotado.

---

## 1. Goal

> *"Si v1.0+1.1+1.2 son la fundación, v1.3 es mantener el juego vivo
> sin que se sienta estancado. Cada mes algo nuevo: un equipo, un evento,
> un tuning, una historia."*

Modelo:

- **Cadence**: 1 release menor por mes (v1.3.1, v1.3.2, …)
- **Sprint length**: 2 semanas (igual que producción normal)
- **Theme rotation**: cada mes tiene un *theme* (e.g., "Copa de Otoño",
  "Mercado de Invierno") que el content cadence respeta
- **Engagement model**: NO daily quests, NO loot boxes. Eventos
  contemplativos consistentes con Pilar 4 "Calm Is The Tempo"

---

## 2. Content cadence pillars

### 2.1 Seasonal events

Eventos calendarizados que llegan con la temporada real (no la in-game).
Cada uno con:

- Mecánica nueva temporal (visible 4-6 semanas)
- Lore narrative AI-driven (v1.2 integration)
- Recompensas cosméticas in-game (sin pay-to-win)

| Mes | Theme | Mecánica suggested |
|-----|-------|--------------------|
| Sep | Pretemporada real | Bonificación XP de scouts en pretemporada |
| Oct | Copa nacional inicio | Sorteo de 8vos publicado in-game |
| Nov | Movida ofensiva otoño | Bonificación a fichajes de delanteros |
| Dec | Mercado invierno hype | Special transfer window mecánica |
| Jan | Mercato invierno real | Mercado activo más volátil |
| Feb | Carnaval (España) | Cosmético: banderines de carnaval en estadio |
| Mar | Recta final liga | Mecánica de bonus por puntos consecutivos |
| Apr | Champions hype | Aparece "European cup invitation" si rank ≥ 4 |
| May | Final liga / playoff | Mecánica de extra-stress en plantilla |
| Jun-Aug | Off-season | Foco en manager-RPG (career calls, vacaciones) |

### 2.3 Generational play

A los 25+ temporadas in-game, el manager se retira → herencia:

| Feature | Sprint estimate |
|---------|----------------|
| Manager retirement event | 2-3 sprints |
| Successor character creation | 1-2 sprints |
| Legacy ledger (trofeos, hitos del predecesor visible) | 1 sprint |
| Optional: "child of" relationship en lore | 1 sprint |

Aspiración: "Tu hijo manager hereda el club que tú levantaste."

### 2.4 i18n introduction

Hasta v1.3 todo es ES-only. v1.3.x introduce localización:

| Release | Idioma | Cobertura |
|---------|--------|-----------|
| v1.3.6 | EN | UI strings primero, staff messages después, AI text último |
| v1.3.7 | PT-BR | Estimación 2 sprints |
| v1.3.8 | FR / DE | Si revenue lo justifica |

Stack: `/localize` skill + JSON-based string catalogs + ICU MessageFormat
en SvelteKit.

### 2.5 Mobile PWA polish

v1.0 incluye un manifest básico. v1.3:

- Sprint dedicado a touch gestures (pinch zoom en canvas v1.1)
- Push notifications opt-in (event: match-day, mercato)
- Offline mode read-only (cache del playthrough, sin advance)
- App-shell preload para cold-start < 1s

| Component | Description | Est |
|-----------|-------------|-----|

## 4. Backlog priorización

Modelo de priorización para cada release menor:

| Eje | Peso | Criterio |
|-----|------|----------|
| Player demand (encuestas + Sentry feature_request) | 40% | Top votado se prioriza |
| Retention impact estimado (vs A/B test data anterior) | 30% | Features que suben retention prevista |
| Cost / effort | 20% | Quick wins primero |
| Strategic (v2.0 enablement) | 10% | Cada cuatrimestre, 1 feature que enables v2.0 |

`/team-live-ops` skill orquesta la priorización mensual.

---

## 5. Acceptance criteria for each v1.3.x release

Cada release menor debe cumplir:

- [ ] 1 feature/event nuevo player-visible
- [ ] No regresiones (tests + smoke check)
- [ ] No nuevas vulnerabilidades (security-audit pasa)
- [ ] Changelog player-facing publicado (`/patch-notes`)
- [ ] Telemetry tracking del nuevo feature (event names definidos)
- [ ] A/B test si la feature lo amerita (sólo cambios grandes)
- [ ] Performance budget mantenido

## 6. Monetization considerations (TBD)

v1.0 lanza gratuito. v1.3 es el momento de decidir monetización si el
demand lo justifica:

| Modelo | Pro | Con | Notas |
|--------|-----|-----|-------|
| Premium one-time | Honest, no friction | Cap LTV bajo | $9.99 USD precio típico |
| Freemium (subscription cosmetic) | LTV escalable, no pay-to-win | Necesita content engine | $4.99/mo premium tier |
| Free + opcional patrons / donations | Open-source friendly | Income variable | Stripe / Patreon |

**Decisión recomendada**: empezar como **Free + donations** durante todo
v1.3. Si DAU > 1000 sostenido, considerar Premium one-time. NO freemium
hasta v2.0 si MMO.

## 7. Risks

| Riesgo | Probabilidad | Impacto | Mitigación |
|--------|-------------|---------|------------|
| Velocidad mensual no sostenible solo dev | Alta | Alta | Releases pueden saltar — no forzar mensualidad si Sprint no tiene 1 feature listo |
| Content cadence se siente repetitiva | Media | Media | Themes rotativos definidos en §2.1; encuestar tras 6 meses |
| Multi-liga balance se rompe | Media | Alta | Cada liga PR pasa `/balance-check` aislado |
| i18n explota copy review work | Alta | Media | Aplicar i18n sólo a strings estables; iteración rápida en ES sólo, broadcast post-estabilización |
| Monetization decision divide a comunidad temprana | Media | Alta | Telegraf con comunidad antes de pivot a paid; documento de transición claro |
