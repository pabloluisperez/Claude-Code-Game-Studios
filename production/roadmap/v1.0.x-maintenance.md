# v1.0.x — Maintenance & Soft-Launch Stabilization

**Window**: 2026-11-18 → 2026-12-15 (4 semanas)
**Status**: Planned
**Owner**: Pablo (solo dev)
**Prev**: v1.0.0 tag + deploy
**Next**: v1.1 unlock

Este es un período de mantenimiento explícito — no contiene features
nuevas. Su objetivo es estabilizar el MVP en producción real antes de
arrancar Pillar B.

---

## 1. Sprint structure

4 sprints de 1 semana cada uno (no 2 semanas como producción normal).
Sprints más cortos para que cualquier hotfix llegue rápido. Sin Sprint
plan formal — el backlog es 100% reactivo a producción.

| Sprint | Window | Focus |
|--------|--------|-------|
| 15 | Wk 1 (2026-11-18 → 24) | Hotfix S1/S2 + observability tuning |
| 16 | Wk 2 (2026-11-25 → 12-01) | Telemetry baseline + GDPR data-export |
| 17 | Wk 3 (2026-12-02 → 08) | Balance pulse + UX polish from feedback |
| 18 | Wk 4 (2026-12-09 → 15) | v1.1 prep — PixiJS spike + GDD seeds |

## 6. Cross-sprint metrics to track

Métricas que vigilamos cada día durante la maintenance window:

| Métrica | Target | Action si excede |
|---------|--------|------------------|
| Sentry error rate | < 1% | > 1% → hotfix antes de añadir features |
| API p95 latency | < 200ms | > 200ms → investigar query lenta o N+1 |
| Soak peak RSS | < 256MB | > 256MB → memory leak hunt |
| DAU | ≥ 20 (signal mínimo) | < 5 → revisar landing + onboarding |
| Day-2 retention | ≥ 40% | < 30% → revisar primera semana del jugador |
| Active S1 bugs | 0 | > 0 → halt feature work |

## 7. Risks specific to maintenance window

| Riesgo | Probabilidad | Impacto | Mitigación |
|--------|-------------|---------|------------|
| Demand fail — no llegan jugadores | Media | Alta | Soft-launch privado primero (5-10 usuarios) antes de público. Si demanda es nula, replantear marketing antes de pasar a v1.1. |
| Soak en prod descubre OOM lento | Baja | Alta | Profiling + heap dumps tempranos. ADR sobre process recycling si se confirma fuga estructural. |
| GDPR data-delete con cascade bugs | Baja | Alta | Test exhaustivo de cascada antes de exponer. Documento en QA. |
| PixiJS spike falla — perf mobile no llega | Media | Media | Si falla, v1.1 baja scope a desktop-first o renderiza menos tiles simultáneos. |
| Onboarding fricción más profunda que esperado | Media | Alta | Sprint 17 reserva 1.5d para iteración profunda; si necesita más, defer Sprint 18 prep. |

## 8. Decisión gate al cierre de v1.0.x

Al cierre de Sprint 18 (semana 4), `/gate-check` formal v1.0.x → v1.1.
Tres outcomes posibles:

- **GO v1.1**: unlock criteria verdes, arrancar Sprint 19 con city-progression
- **EXTEND v1.0.x**: criterios no verdes pero arreglables. Añadir 2-4 semanas
  más de mantenimiento con scope específico.
- **PIVOT v1.0**: demand fail, replantear product-market fit antes de invertir
  en Pillar B. No es esperado — fallback only.
